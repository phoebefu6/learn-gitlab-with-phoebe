Container registry and templates

Session 6 gave Penwood a staging and a production environment. Tonight is about the two things every deploy job quietly depends on: an image to deploy, and a pipeline file that five people can share without copying it five times. Then include and extends let one small template file carry the dependency scan for the whole team. What a container or an image actually is belongs to a later course; here you only see where it lives and how a job gets there.

Part 1 · covers the registry path, CI_REGISTRY_IMAGE and the job's own login

The project's own registry

6 min live

The container registry page says the path of a container repository "always matches the related project's repository path". So Penwood's images live at registry.gitlab.com/penwood/data/pipelines, the same three segments as the project URL from session 1, with up to two optional name levels below it. The registry is on every tier, stores Docker V2 and OCI formats, and is visible either to everyone with access to the project or to project members only. What an image is, how a container runtime builds and runs one, is a later course; this page takes only where it is stored and how a job signs in.

Live Three variables and one login line 3 min▶

The predefined variables page lists CI_REGISTRY_IMAGE as the "Base address for the container registry", set only when the registry is enabled for the project. The authentication page gives the login a job should use: echo "$CI_REGISTRY_PASSWORD" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin. Those three variables exist in every job without anyone creating them, and the password is the job token, which "has read (pull) and write (push) access to the container registry of the project that runs the job". Penwood's build-image has tagged $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA since session 3; tonight the login line goes in front of the push so the tag has somewhere to land. No personal token, no masked variable from session 4, nothing to rotate.

Self-study Visibility, formats and what the quota counts 2 min▶

The registry page lets a project set its registry to "Everyone With Access" or "Only Project Members"; Penwood's project is private, so both read the same for outsiders and the setting matters only if the project is ever opened up. It accepts Docker V2 and OCI image formats. The storage quotas page, as of 2026-10-29, says each project in a Free namespace has 10 GiB of free storage, that only the repository and LFS count, and that the container registry, package registry and artifacts are excluded; a project over 10 GiB becomes read-only unless storage is purchased. So images do not eat the project's 10 GiB, but the free user limit page's read-only state over five users does stop writes to registries. Re-verify the tier page before relying on it.

Real world

The free user limit page says a private top-level namespace over five users is "placed in a read-only state", and session 1 listed what that covers: repositories, LFS, packages and registries. Constructed: Penwood invites a sixth person to look at the board; the next push to main builds the image fine, then publish-image fails at the push because the registry will not accept a write. The pipeline is red for a reason that has nothing to do with the YAML. The fix is on the members page, not in the job.

Part 2 · covers include:local, hidden jobs and how extends merges

Include, then extend

6 min live

A pipeline file grows by copy and paste until two jobs that should be identical are not. GitLab's answer has two halves. include pulls another YAML file into the configuration before anything else is read, and the includes page says the main file "takes precedence" over what it includes. extends lets a job inherit from a hidden job, one whose name starts with a dot and which never runs on its own, through what the YAML reference calls a "reverse deep merge based on the keys". Penwood puts one hidden job in ci/scan-template.yml and extends it from scan-dependencies.

Live What "reverse deep merge" means in practice 3 min▶

The YAML reference says extends is a "reverse deep merge based on the keys", that the values of keys are not merged, that up to eleven levels of inheritance work, that more than three is best avoided, and that a job may extend several parents. In practice: GitLab builds the job from the hidden job upward, then lets each key the job itself defines replace the parent's. For Penwood that means scan-dependencies gets image, script and allow_failure from .dependency-scan, keeps its own stage and needs: [], and if someone one day adds a script to the job, the template's script is replaced whole, not appended to. The bench in session 8 shows the resolved job: after the include its file holds 14 jobs, and scan-dependencies has a script it never wrote.

Self-study Which file wins, and which part of that is the bench's 2 min▶

Two ordering facts come from the includes page: includes are evaluated first and merged with .gitlab-ci.yml, which "takes precedence"; and between several includes, the last one wins. What the page does not spell out is how deep that merge goes inside a job. The bench's convention is a key-level deep merge, includes in order and then the main file last; say "the bench's convention" when you quote it, not "GitLab". The practical rule is the same either way: define a key once, in the template, and override it in the main file only when you mean to. Two definitions of the same hidden job in two included files is a defect waiting for someone to reorder the include list.

Real world

The YAML reference says allow_failure: true lets a job fail while the pipeline still passes, with an orange warning, the status GitLab shows as passed with warnings. Penwood's template sets exactly that on the scan, so a new advisory in a dependency never blocks a merge; it shows orange and someone reads it. Constructed consequence: in week three the orange is there every day and nobody opens it. The template made the scan cheap to ignore. Deciding when a scan should block is a team rule, not a keyword; allow_failure only records the decision you made.

Part 3 · covers include:template, include:project, remote URLs and the limits

Templates GitLab ships

5 min live

The includes page lists four ways to include: local, a file in the same project; project, a file in another project on the same instance; remote, a URL; and template, a file GitLab ships with the application. The pricing page, as of 2026-10-29, lists "Static Application Security Testing" in the Free tier, and GitLab's own scanners arrive in a pipeline through include:template. The exact template file names are listed on the includes page and the scanner pages; copy them from there rather than from memory, because a template path that does not exist fails the pipeline at creation.

Live Why a template is still just an include 3 min▶

A shipped template is a YAML file like Penwood's own, written by GitLab, merged by the same rule: includes first, main file wins. That is what makes it safe to adopt. If a shipped scanner job declares a stage Penwood's file does not have, the main file can redefine that job's stage and the override takes precedence. The pricing page puts Static Application Security Testing in Free as of 2026-10-29; which scanners beyond that are Free, and what each one does, is on the scanner pages and changes between releases, so read the badge on the page the day you add it. Penwood's constructed .dependency-scan is a stand-in: a small local template that behaves like a shipped one, so the merge can be watched on the bench without depending on a scanner this page did not read.

Self-study Sharing across projects: project over remote 2 min▶

When Penwood's finance subgroup gets its own project next year, the scan template should not be copied into it. The includes page prefers include:project, a file in another project on the same instance, over include:remote, a URL: the project version is read with GitLab's own permissions and pinned to a ref you name, where a URL is whatever is at that address when the pipeline is created. A single penwood/ci-templates project holding scan-template.yml, included by ref from every pipeline, is the pattern. The limits are generous for a team of five: up to 150 includes and 30 seconds to resolve them; a nested include counts toward the 150.

Real world

Constructed: Penwood's analyst finds a scan template on a public URL and adds it with include:remote. It works for a month. Then the file at that URL changes its job names and the pipeline fails at creation with a message about a job that no longer exists; nothing in Penwood's repository changed. Moving the file into a project of their own and including it by ref makes every change to the template a merge request someone reads. The includes page states the preference for project over remote; this is the reason behind it.

Check yourself

Three questions

Clear all three and Builder session 7 gets stamped in your passport.

1 · Penwood renames the project pipelines to data-pipelines. What happens to the address its images are pushed to?

The container registry page: the path "always matches the related project's repository path". The address is derived from the tree, never chosen, so renaming the project renames the registry path; anything outside GitLab that held the old address now points at nothing.

2 · .dependency-scan in the included file sets script and allow_failure: true. scan-dependencies in the main file sets stage, needs: [], extends: .dependency-scan and its own one-line script. What does the resolved job run?

The YAML reference calls extends a "reverse deep merge based on the keys" and says the values of keys are not merged: the job's own key replaces the parent's whole. Keys the job does not define, here allow_failure, are inherited. The main file wins over the include.

3 · A job needs to push to Penwood's own registry. Which credential does the authentication page's login line use, and what can it reach?

The login is echo "$CI_REGISTRY_PASSWORD" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin, and the job token "has read (pull) and write (push) access to the container registry of the project that runs the job". Nothing to create, store or rotate.
