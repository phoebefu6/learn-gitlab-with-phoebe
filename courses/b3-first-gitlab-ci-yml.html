Learn GitLab · Builder session 3 of 8

Your first .gitlab-ci.yml

A pipeline in GitLab is one file at the root of the project. It names stages, puts jobs in them, and gives every job a script. Commit it and GitLab.com's instance runners pick it up without any setup on Free. Tonight Penwood, a constructed five-person logistics-analytics team, writes that file by hand for its data pipelines: five stages, fourteen jobs, no shortcuts yet. The bench in session 8 parses exactly this stages-only version and reports the first green run at 30:08 on the clock and 66.30 compute minutes on the bill. Both numbers are canon; the job durations behind them are constructed.

Part 1 · covers stages, stage, script, image and default, and where a stage-less job lands

Stages, jobs, script

6 min live

The YAML reference gives the shape in three keywords. stages is a list at the top of the file that fixes the order. A job is any top-level key that is not a reserved word, and it carries stage to say where it runs and script to say what. The reference is blunt about the last one: script is required for every job except trigger jobs. Everything else, image, default, variables, needs, rules, is optional and arrives in later sessions.

Live What a stage promises 3 min▶

The reference says "Jobs in the same stage run in parallel", and the next stage starts only after the previous stage's jobs succeed. That is the whole contract of a stage: everything inside it may run at once, nothing after it starts until all of it is done. Penwood writes five stages because its work has five kinds: lint the YAML and SQL, build an image, the compiled models and the docs, test five ways, publish the image and docs, deploy to staging and production. The pipeline architectures page calls this basic shape "easier to maintain" and also "not the most efficient"; session 5 earns the efficiency with needs. Tonight you take the simple contract on purpose, because a file you can read beats a file that is fast.

Self-study The defaults you did not write 2 min▶

If you write no stages line, GitLab uses .pre, build, test, deploy, .post. If a job has no stage, it uses test. A pipeline whose only jobs sit in .pre and .post does not run at all. The default block holds values every job inherits unless it sets its own; Penwood puts image: python:3.12-slim there once, and the reference says a job's own image overrides it. The job's script runs inside that image on whichever runner picks the job up. What an image is belongs to a later course on containers; here it is the environment your script runs in, named once.

Self-study Who runs the script: the instance runner on Free 2 min▶

The runner docs describe a runner as "an application that works with GitLab CI/CD to run jobs in a pipeline", and the scope page says "On GitLab.com, instance runners are enabled in all projects by default". So Penwood commits the file and a runner it never installed picks the jobs up. The runner asks GitLab for jobs with its own token; each job then runs with a job token of its own, which session 7 uses to log in to the registry. Group runners and project runners exist for when you want your own machines; the Leader track's session 2 weighs that. One practical note from the pricing FAQ, read 2026-10-29: a credit card is required to use GitLab.com's shared runners even on the $0 tier; re-verify the tier page before relying on it.

Real world

Constructed: Penwood's analyst adds a quick docs-check job to the file, copies script from docs-build and forgets stage. She expects it beside the linters. It appears in the pipeline graph under test, after the 382 s image build, exactly as the reference says: a job without stage uses test. Nothing failed, so nobody noticed for a week that a 10-second check was waiting eight minutes for a stage it had nothing to do with. The fix is one line. The habit is to read the graph after every commit to the file, not only when it goes red.

Part 2 · covers the first green run, what the graph shows and why it takes as long as it does

The first green

6 min live

Penwood's complete stages-only file has fourteen jobs. The bench parses it as a push to main with no runner cap and reports the canon for rung r1: thirteen jobs ran, one (deploy-production, when: manual) waits for a click, wall clock 30:08, serial time 66:18, 66.30 compute minutes. The longest single job is 894 s, under fifteen minutes. The other fifteen minutes are the stage contract doing what it promised.

Live Read the green pipeline before you celebrate it 3 min▶

Green answers one question: did every job that ran exit zero. It does not say how many jobs ran, how long they waited, or what they cost. On r1 the bench's critical path is lint-sql, build-image, nightly-backfill, publish-image, deploy-staging: 107 + 382 + 894 + 245 + 180 = 1,808 s, which is 30:08. Note what is on that path: a nightly backfill that has no business running on a push to main, and an image build that every test waited for even though only integration-tests uses the image. Both are the stage contract working exactly as written. Session 5 removes the backfill from pushes with a rule and lets tests start from compile-models with needs; the bench reports that version at 26:22 and then 19:17. Tonight, read the graph, name the path out loud, and leave the file simple.

Self-study One manual job and what blocked would have meant 2 min▶

deploy-production carries when: manual at the job level, outside any rules. The job control page says that for a manual job written this way allow_failure defaults to true, so the pipeline can finish and show success while the button is unclicked. Write the same when: manual inside a rules entry and the default flips to false: "The pipeline stops at the stage where the job is defined" and the status reads blocked. Penwood wants the blocking version for production, and session 6 moves the keyword inside rules for that reason. The bench's convention, not GitLab's documented behaviour, is that a manual job is never scheduled and anything downstream of it is reported as waiting; the reference fixes no duration for a manual gate.

Real world

The YAML reference documents a second colour of green. A job with allow_failure: true that fails shows an orange warning and the pipeline still passes. Teams add it to a flaky test "for now", the pipeline reads passed with warnings for months, and the merge button never once refused. Constructed: Penwood's lead sets the rule that allow_failure appears in the file only with a comment naming the issue number that will remove it. The keyword is fine; a green that nobody reads is the problem.

Part 3 · covers compute minutes, cost factors and the Free quota one run eats into

What a minute costs

5 min live

The clock the team feels is the wall clock, 30:08. The clock the quota counts is a different one. The compute minutes page says "The usage of instance runners ... is measured in compute minutes", and the bench computes them the way the page describes: add every job's seconds, divide by 60, multiply by the runner's cost factor. On r1 that is 3,978 s of serial time, 66:18, which at cost factor 1 is 66.30 compute minutes for one green run. Free gives 400 a month, as of 2026-10-29.

Live Six runs a month is not a pipeline 3 min▶

Divide 400 by 66.30 and you get 6.03: six green runs of the stages-only file fit in Penwood's Free month, the seventh does not. That is the arithmetic, not a bench measurement, and it assumes every job runs on a Linux small runner at cost factor 1. Penwood's constructed month is 24 merge-request pipelines, 12 pushes to main and 4 schedules, forty runs. The stages-only file runs all thirteen jobs every time, so the gap is not close. The bench's scorecard on the final file, with rules and needs, still lands at 1,803.8 compute minutes a month, 450.95% of 400; the stages-only file would cost more, because every run executes every job. The lesson lands tonight so that sessions 4 and 5 are read as cost tools, not only speed tools: rules:changes to skip jobs, fewer scheduled runs, or runners the quota page does not measure (re-verify that page; it suggests private runners for some jobs and does not say your own runners are exempt), or Premium's 10,000 minutes at $29 per user a month billed annually, as of 2026-10-29.

Self-study Cost factors and the resets 2 min▶

The compute minutes page lists the factors for GitLab.com's hosted Linux runners: small 1 (x86-64 and Arm64), medium 2, large 3, xlarge 6, 2xlarge 12. A 382 s image build on a large runner would be counted as 19.10 minutes, not 6.37; that is arithmetic on the page's factors, your numbers will differ with your durations. Usage "resets to 0 for all namespaces on the first day of each month". The page says "Enforcement measures are applied when you exceed your quota" and sends you elsewhere for what they are; nothing here describes them, because the page read did not. The honest limit on everything in this Part: durations are constructed, the bench parses and schedules rather than running anything, and every tier number is dated 2026-10-29.

Real world

Constructed: in Penwood's first week on the file, the two analytics engineers push to main eleven times to fix YAML indentation, one line per push, and each push runs all thirteen jobs. By Friday the usage page reads more than the month allows and the team has not yet shipped a model. Nothing was misconfigured. A stages-only file bills every job on every push; that is why the first merge request in session 2 mattered, why rules arrive in session 5, and why the lint stage in tonight's build-along is the one you run by hand before you commit.

Build-along

Penwood's lint and build stages, by hand

★ 22 min · everyone builds

Open the project from session 1 and the feature/orders-dedupe branch from session 2. You will write a .gitlab-ci.yml with two of Penwood's five stages from memory, commit it to the branch, read the pipeline graph, then compare your file with the stages-only file the bench parses. Penwood's scripts call tools that do not exist in your project; the point is the shape, so let them fail or swap in echo. Everything runs on GitLab.com Free as of 2026-10-29; the durations drawn below are constructed and your numbers will differ.

Write the skeleton without looking. On the feature/orders-dedupe branch, create .gitlab-ci.yml at the project root. Type the stages list with all five names, a default block with one image, and nothing else yet. Say what each stage will hold before you write a job.

★ The skeleton (Penwood, constructed)stages: - lint - build - test - publish - deploy default: image: python:3.12-slim

Add the two lint jobs. Each job is a top-level key with stage: lint and a script list. Keep the names lower case with hyphens; they appear on every graph and in every needs list later. If your project has no YAML or SQL to lint, keep the shape and swap the command for an echo.

★ Stage lint, two jobs (excerpt of stages-only.yml)lint-yaml: stage: lint script: - python -m yamllint pipelines/ lint-sql: stage: lint script: - python -m sqlfluff lint models/

Add the three build jobs. Same shape, stage: build. The image build uses two predefined variables, CI_REGISTRY_IMAGE and CI_COMMIT_SHORT_SHA; session 7 explains the first, session 4 the rest. Quote the line because of the colon, as the data file does. Then commit to the branch and open the merge request's pipeline tab from session 2.

★ Stage build, three jobs (excerpt of stages-only.yml)build-image: stage: build script: - 'docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .' compile-models: stage: build script: - python pipelines/compile.py --out build/ docs-build: stage: build script: - python docs/build.py

Read the graph, not the badge. Two columns of jobs: two in lint, three in build. Watch that no build job starts until both lint jobs finish, even though lint-yaml finishes first. In the pipeline list, the run from the merge request carries a merge request label when the file has rules for it; tonight's file has none, so you get a branch pipeline, which is fine for now and is session 5's subject.

★ What you should see, roughly (your numbers will differ)stage lint lint-yaml passed lint-sql passed stage build build-image passed compile-models passed docs-build passed (or failed, if the tools are not in your project: the shape is the lesson) bench canon for the same two stages of r1: lint ends 1:47 · build ends 8:09 · 489 s

Diff your file against the stages-only file. Open stages-only.yml from the bench's data file and lay it beside yours. The differences you should find: it has nine more jobs across test, publish and deploy, a variables block with PYTHON_VERSION and PIPELINE_OWNER, an environment on both deploy jobs, and when: manual on deploy-production. The differences you should not find: anything missing from a job other than stage and script. Add the remaining nine jobs from the file, commit once, and read the graph again.

★ The tail of stages-only.yml (excerpt)deploy-staging: stage: deploy environment: name: staging script: - python deploy/run.py --target staging deploy-production: stage: deploy when: manual environment: name: production script: - python deploy/run.py --target production
✗ The step to skipWriting a job without a stage "because it is just a quick check". The YAML reference: a job without stage uses test. Your quick check now waits for every build job to finish, costs the same compute minutes wherever it sits, and shows up in a column you did not expect. Name the stage, every job, every time.

Check yourself

Three questions

Clear all three and Builder session 3 gets stamped in your passport.

1 · A job in Penwood's file has a script but no stage. The file lists five stages. Where does the job run?

The YAML reference: a job without stage uses test. script is the keyword whose absence breaks the job; stage has a default that quietly places it.

2 · On bench rung r1, integration-tests finishes at 1,219 s but publish-image does not start until 1,383 s. Which job sets that start, and why?

A stage starts only after the previous stage's jobs succeed. With no needs in the file, publish waits for the slowest test job, the 894 s backfill that ends at 23:03. r1 has unlimited runners on the bench, so no queueing is involved.

3 · One r1 run: wall clock 30:08, serial time 66:18, every job on a Linux small runner. What does the quota count for that run?

Compute minutes add every job's time; parallel stages do not reduce them. 3,978 s / 60 = 66.30 at factor 1. Six such runs fit in 400 a month on Free, as of 2026-10-29; re-verify the tier page before relying on it.
