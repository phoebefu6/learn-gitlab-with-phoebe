Learn GitLab · Leader session 5 of 6

Governance without friction

Governance has a reputation for slowing teams down because it is usually bolted on afterwards: a sign-off form here, a change-advisory meeting there. GitLab puts the controls at the place the change already has to pass through, the branch and the merge request, and most of them are on the Free tier and switched on before anyone configures them. Penwood, a constructed five-person logistics-analytics team on GitLab.com Free, needs production data pipelines that nobody can change alone and credentials that no feature branch can read. Tonight is which controls are free, which cost a tier, what the free substitute for each paid control is, and the one control that looks stronger than it is.

Part 1 · covers protected branches, who may push and merge, and why the merge request is the gate

The branch is the control point

6 min live

Every change to Penwood's pipelines ends as a commit on main. If nothing can reach main except a merge request that a Maintainer merges, then the merge request is where review, the pipeline and the record of who agreed all happen, without a meeting. The protected-branches page says "The default branch for your repository is protected by default"; a new rule selects Maintainers for "Allowed to push and merge", and force push is off by default. The control exists before you configure anything. The leader's job is to leave it on and to keep the Maintainer list short.

Live What the default rule says, in the docs' words 3 min▶

Three sentences from the protected-branches page do most of the governance work. "The default branch for your repository is protected by default." When you add a rule, it selects Maintainers for "Allowed to push and merge". Force push is off by default, so history on main cannot be rewritten by anyone the rule allows to push. Put those next to two lines from the permissions page: a Developer can "Push code to non-protected branches, create merge requests, and run CI/CD pipelines"; a Maintainer can "Manage branches, merge requests, CI/CD settings, and project members". Penwood's analyst and its second analytics engineer are Developers, so the figure above is their only route: a feature branch, a merge request, and a Maintainer's merge. The record of who opened, who reviewed, which pipeline ran and who merged is the merge request itself. That is the audit trail, and nobody filled in a form to create it.

Self-study Wildcards, the most permissive rule, and the Premium group-level version 4 min▶

Rules can match a pattern such as release/*, so every release branch is protected the moment it is created. When two rules match the same branch, the most permissive one wins, which is the trap: a loose wildcard rule added "for convenience" quietly loosens a tighter rule on the same branch. Review the rule list, not just the rule you added. Protected branches set at the group level, so that every project under penwood inherits them, are Premium and Ultimate. On Free, Penwood sets the rule per project; with one project that is one rule, and the control list tonight records that it must be repeated for each project the team creates later.

The seam, in one line: what a pull request is for people who do not code lives in the GitHub course on branches and pull requests, and branching itself in GitHub for builders; this page takes only what GitLab does with the branch as a control: who may push, who may merge, and what the rule refuses.

Live Why "Maintainers only" is a governance decision, not an IT setting 2 min▶

The rule is only as strong as the Maintainer list. Penwood has two people who can merge into main: the data lead as Owner and one analytics engineer as Maintainer. That is the whole production-change authority of the team, written as two names, and it is the leader's list to keep. A third Maintainer added "so releases are not blocked on holiday" is a real decision with a real trade-off, and it belongs on the control list with a date next to it. Governance without friction is not governance without decisions; it is making the decisions where the platform already enforces them.

Real world

Constructed: Penwood's analyst fixes a column name in models/orders.sql late on a Thursday and tries to push it straight to main to catch the nightly backfill. The push is refused; the analyst is a Developer and the default rule allows only Maintainers. So the fix goes to feature/orders-dedupe, a merge request opens, the merge request pipeline runs the eight jobs from session 4, and the analytics engineer merges it twenty minutes later. Nothing about that was a process the team designed. It was the default rule, left on, doing the job a change-approval meeting would have done more slowly.

Part 2 · covers required approvals, Code Owners, protected environments and compliance frameworks, with the Free way for each

What Premium adds, and the Free substitute

6 min live

The paid tiers do not add controls Penwood lacks. They add enforcement of controls Penwood can already run by convention. On Free, anyone with at least Developer can approve a merge request, and the approvals page says "These approvals are optional and don't prevent merging without approval". Required approval rules and Code Owner approval are Premium and Ultimate; so are protected environments and compliance frameworks. For each of the four there is a Free way that does most of the work, and the honest question is how much the gap between convention and enforcement is worth to you.

Live Approvals on Free are a signal, not a lock 3 min▶

On Free, anyone with at least Developer can approve a merge request, and the approvals page is explicit that "These approvals are optional and don't prevent merging without approval". So an approval on Free is a recorded statement, "I looked at this", that the merge request keeps forever, and the thing that actually stops an unreviewed merge is the branch rule from Part 1: only a Maintainer can merge. The Free convention, then, is two lines on the control list: "a second person approves before merge" and "the Maintainer does not merge their own merge request". Required approval rules, Premium and Ultimate, turn those two lines into something the merge button checks. Code Owner approval, also Premium and Ultimate, goes further: the people named for a path must approve changes to it. On Free the CODEOWNERS file can still live at CODEOWNERS, docs/CODEOWNERS or .gitlab/CODEOWNERS; it does not block, but it tells every reviewer who should have been asked, and a Maintainer can read it before merging.

Self-study The one Free substitute the platform enforces: a blocking manual job 4 min▶

Protected environments, Premium and Ultimate, mean that "only people with the appropriate privileges can deploy to it". Penwood's Free version is in the pipeline file: deploy-production has when: manual inside its rules. The job-control page is specific about what that does. For a manual job defined inside rules, allow_failure defaults to false, so the job is blocking: "The pipeline stops at the stage where the job is defined", and the pipeline's status is blocked until someone clicks. Nothing deploys to production by accident, and the click is recorded against a name. What this does not do is restrict who may click; anyone who can run the pipeline can. That is exactly the gap protected environments close, and it is the first thing the control list should say about the Premium decision: Penwood is five people who all sit in one room, so the gap is small; a thirty-person group would price it differently.

Compliance frameworks, Premium and Ultimate, are "a label to identify that your project has certain compliance requirements". Penwood's Free substitute is the control list itself, kept in the repository and re-read in every merge request that touches a setting. Epics, also Premium and Ultimate, are out of scope here; Builder session 1 covers the Free board.

Live How to decide whether a tier is worth it 2 min▶

Write the convention first, run it for a month on Free, and count the times it was not followed. Zero means the convention holds and the tier buys you nothing yet. A number above zero is the cost of enforcement you are already paying in incidents, and that number, not the feature list, is the argument for Premium. Premium is $29 per user a month billed annually as of 2026-10-29; re-verify the tier page before relying on it. For five people that is a number you can hold next to one production mistake and decide.

Real world

The job-control page documents the two faces of a manual job. Outside rules, when: manual defaults allow_failure to true, so the pipeline can pass with the manual job never run; inside rules it defaults to false, the pipeline stops at that stage and shows blocked. Same keyword, opposite governance outcome, decided by where it is written. Penwood's file puts when: manual inside the rule on purpose; the bench in Builder session 8 shows deploy-production waiting for a click on every run to main. A leader does not write the YAML; a leader asks which of the two faces the production job has.

Part 3 · covers protected and masked variables, where a variable is visible, and what masking does not promise

Masked is not secret

5 min live

Credentials are the governance question a data team feels most, because a pipeline that deploys needs them and a feature branch that anyone can push to runs the same pipeline. GitLab offers two switches on a CI/CD variable. Protected sends the variable only to pipelines on protected branches or tags. Masked prints it as [MASKED] in the job log. The variables page is candid about the second: masking "is not a guaranteed way to prevent malicious users from accessing variable values". Read the figure as a variable resolving, not as a vault.

Live Three places a value can live, and who can read each 3 min▶

A value in the variables: block of .gitlab-ci.yml is in the repository, and the variables page says it plainly: "Variables saved in the .gitlab-ci.yml file are visible to all users with access to the repository." Penwood's file keeps only PYTHON_VERSION and PIPELINE_OWNER there, and nothing else should ever join them. A project variable set in the CI/CD settings is the second place; by default it is sent to every pipeline, including one on a branch a Developer just pushed. Marking it protected changes that: it goes only to pipelines on protected branches or tags, which after Part 1 means only pipelines on main. Marking it masked changes only the log: a value that is one line, has no spaces and is at least eight characters is printed as [MASKED]. The control list needs one row that says: "every credential is a protected variable; masked as well where the format allows; none in YAML".

Self-study What masking cannot promise, and what to ask instead 3 min▶

Masking is a text substitution on the job log. A job script that writes the value to a file, encodes it, splits it across lines or sends it somewhere else is not affected; the page's own words are that masking "is not a guaranteed way to prevent malicious users from accessing variable values". So the question a leader asks is not "is it masked" but "which pipelines can receive it at all", and the answer that holds is "only pipelines on a protected branch, which only Maintainers can merge into". That chains Part 3 back to Part 1: the branch rule is the secrets control too. Where a variable's precedence comes from, job over global over predefined, is Builder session 4's territory and is not retaught here.

Real world

The variables page documents both halves. Protected variables are available only to pipelines that run on protected branches or protected tags; masked values must be a single line, contain no spaces, be at least eight characters long, and are shown in job logs as [MASKED]; and the same page says masking "is not a guaranteed way to prevent malicious users from accessing variable values". Constructed: Penwood's warehouse token is both protected and masked. A Developer who opens a merge request from feature/orders-dedupe gets a pipeline that never receives the token at all, which is the sentence the finance partner wanted to hear, and the one the log alone could not have proven.

Build-along

Penwood's one-page control list

★ 20 min · everyone builds

One page, three columns: the control, the gap it closes, and the tier it needs with the date you checked. Penwood's is filled below as a constructed example; yours lists your own controls. Every row is a sentence you can defend in an audit conversation, and every tier badge is something you read on a docs page, not something you remember. No GitLab account is needed tonight.

List the gaps first, then the controls. Start from what must never happen: a production change nobody reviewed, a production deploy nobody chose, a credential in a log anyone can read. One row per gap. Then name the GitLab control that closes it and copy its tier badge from the docs page, with today's date. Penwood's constructed list is below.

Homework

Before session 6

25 min
  1. Finish your control list with a tier badge and a date on every row. Any row whose badge you could not find on a docs page is marked "unverified", not guessed.
  2. Count the people who can merge into your production branch today, in whatever tool you use. Write the number and the names; if you cannot, that is the first row of the list.
  3. Find one credential your pipelines use and answer two questions in writing: which branches can receive it, and where it is stored. If the answer to the second is "in the pipeline file", say so.

Check yourself

Three questions

Clear all three and Leader session 5 gets stamped in your passport.

1 · A Developer on Penwood's project (constructed) approves a merge request into main on GitLab.com Free. What does that approval do?

The approvals page: users with at least Developer can approve, and "These approvals are optional and don't prevent merging without approval". Required approval rules are Premium and Ultimate. On Free the lock is the branch rule, not the approval.

2 · Penwood's deploy-production job has when: manual inside its rules. What does the pipeline do when it reaches that job on a push to main?

The job-control page: inside rules, when: manual defaults allow_failure to false, "The pipeline stops at the stage where the job is defined", status blocked. Outside rules the default flips to true and the pipeline can pass without it. Where the keyword sits decides the governance outcome.

3 · Penwood's warehouse token is a project variable marked masked but not protected. A Developer pushes to feature/orders-dedupe and the branch pipeline runs. What is true?

Only the protected switch limits which pipelines receive a variable: protected branches and tags. Masking prints [MASKED] in the log and, in the variables page's words, "is not a guaranteed way to prevent malicious users from accessing variable values". Protected first, masked as well.
