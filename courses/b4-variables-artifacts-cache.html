Learn GitLab · Builder session 4 of 8

Variables, artifacts, cache

Session 3 got Penwood's pipeline green. Tonight is about what moves between its jobs. A variable is a value a job reads, and ten places can define it, so the question is never "what is it set to" but "which definition wins". An artifact is a file a job hands to the jobs after it, kept by GitLab and downloaded by default in later stages. A cache is a folder the runner may or may not still have from last time. Penwood, a constructed five-person logistics-analytics team on GitLab.com Free, needs all three this week: compile-models writes build/ that three test jobs read, the test jobs install the same packages every run, and a publish token has to exist somewhere other than the YAML everyone can read.

Part 0

Three things that move between jobs

Every job in a GitLab pipeline starts in a fresh environment with a clone of the repository and nothing else. That is the fact behind tonight. If unit-tests needs the build/ folder that compile-models wrote, something has to carry it across, and that something is an artifact. If the same job installs the same packages every run, a cache may spare it the download, and the word is "may". If a job needs a token, the token arrives as a variable, and the place you define it decides who can read it. Penwood is constructed: its people, durations and file names are invented for these pages, and nothing on this page runs GitLab for real.

Part 1 · covers variable precedence, YAML versus settings, protected and masked

Where a variable comes from

6 min live

Penwood's penwood.yml opens with variables: PYTHON_VERSION: '3.12'. That is one of ten places the value could come from. The CI/CD variables page lists them in order, highest first: variables from a policy, variables typed on a manual job, variables set when the pipeline is run, project settings, group settings, instance settings, dotenv reports, the YAML (rules:variables, the job's own, workflow:rules:variables, then the default block), deployment variables, and finally the predefined ones GitLab sets itself. A job reads the first definition it meets walking down that list. Inside the YAML alone the rule is simpler: a job's variables override the global ones.

Live YAML variables are public to the repo 3 min▶

The variables page says it without softening: "Variables saved in the .gitlab-ci.yml file are visible to all users with access to the repository." That makes the YAML the right place for PYTHON_VERSION and PIPELINE_OWNER, which Penwood wants everyone to see and change by merge request, and the wrong place for anything a Reporter should not read. Penwood's finance partner is a Reporter and can view code, so a token in the YAML is a token the finance partner has. Settings variables sit above the YAML in precedence, which has a practical side effect: a project setting named PYTHON_VERSION silently beats the one in the file, and the pipeline runs a version nobody can see in the repo. Name settings variables so they cannot collide with YAML ones.

Live Protected means "only on protected refs", masked means "hidden in logs" 2 min▶

The two flags on a settings variable do different jobs. A protected variable is passed only to pipelines running on protected branches or tags. Since main is protected by default (session 1 saw the rule), Penwood's publish token marked protected exists on a push to main and does not exist in a merge request pipeline from feature/orders-dedupe. That is the point: a feature branch anyone with Developer can push to never receives the token. A masked variable must be a single line with no spaces and at least 8 characters, and the job log prints [MASKED] where the value would appear. The page then says masking "is not a guaranteed way to prevent malicious users from accessing variable values". A script that base64-encodes the value, or writes it to a file that becomes an artifact, defeats masking without trying. Protected is the control; masked is a courtesy to whoever reads the log.

Self-study The predefined ones Penwood already uses 2 min▶

At the bottom of the precedence list sit the variables GitLab defines for every job. Penwood's file already reads four of them. CI_PIPELINE_SOURCE is merge_request_event in a merge request pipeline and push for a push. CI_COMMIT_BRANCH is "Available in branch pipelines, including pipelines for the default branch" and is not set in merge request or tag pipelines, which is why the publish and deploy jobs with $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH are never added to a merge request pipeline (session 5 reads that off the bench). CI_REGISTRY_IMAGE is the "Base address for the container registry", set only when the registry is enabled (session 7). CI_COMMIT_SHORT_SHA tags the image. Because these are lowest in precedence, defining your own CI_COMMIT_BRANCH in the YAML would override GitLab's; nothing stops you, and nothing good follows.

Real world

Constructed: Penwood's analyst needs the publish token for a quick local test and pastes it into the YAML as PUBLISH_TOKEN: glpat-... on a feature branch, meaning to remove it before merging. The merge request pipeline runs; the job log shows the token in plain text because YAML variables are never masked; the branch is visible to all five people including the Reporter. Nothing about this is a GitLab flaw. The variables page said the YAML is visible to everyone with repository access, and it was. The fix is to rotate the token and put the new one in project settings, protected and masked, so the feature branch never receives it at all.

Part 2 · covers artifacts:paths, default download in later stages, expiry and the GitLab.com size limit

Artifacts move results forward

6 min live

compile-models writes build/. unit-tests, data-quality-tests and integration-tests read it. They run in a different stage, in a fresh environment, possibly on a different runner. The job artifacts page is what makes this work: "By default, jobs in later stages automatically download all the artifacts created by jobs in earlier stages." A job declares what it is handing forward with artifacts:paths; GitLab archives those paths when the job succeeds, stores the archive, and later jobs download it before their script runs. With needs, the needed jobs' artifacts are downloaded too, because artifacts: true is the default for a needs entry.

Live Declare on the producer; the consumers get it for free 3 min▶

All the work is on compile-models: artifacts: paths: - build/. The three test jobs change nothing and still find build/ in their working directory, for two reasons that both apply here. They are in a later stage, so the default download covers them. And each one lists compile-models in needs, and a needs entry downloads that job's artifacts unless you write artifacts: false. Artifacts are "collected from successful jobs by default", so if compile-models fails there is no archive, and the test jobs do not run anyway because the stage did not succeed. The archive is stored by GitLab, not left on the runner, which is the difference from a cache and the reason an artifact is a promise.

Self-study Expiry, the kept pipeline, and the 1 GB line 3 min▶

expire_in says how long GitLab keeps the archive after the job finishes. Leave it out and the instance default applies; the page read on 2026-10-29 does not state what that default is on GitLab.com, so no number is quoted here, and the honest move is to set one. Penwood uses 1 week on build/: long enough to debug a failed Friday pipeline on Monday, short enough that forty pipelines a month do not pile up. Two more rules from the page. Artifacts of the latest successful pipeline per ref are kept regardless of expiry, so the newest green main always has its build/ to download. And on GitLab.com an archive is limited to "1 GB compressed"; a build/ that holds compiled SQL models is kilobytes, a build/ that someone adds a sample parquet file to is not. The storage quotas page adds, as of 2026-10-29, that artifacts are excluded from the 10 GiB per project count that only the repository and LFS fill; re-verify the tier page before relying on it.

Real world

Constructed: before tonight, Penwood's compile-models had no artifacts block. The job ran, wrote build/ and finished green. unit-tests then started on a clean clone, found no build/, and failed with a missing-directory error from the test runner. The analyst's first guess was that compile-models had not run; it had. The second guess was a path typo; there was none. The mechanism is the fresh environment per job: nothing crosses the stage boundary unless a job declares it. One artifacts:paths line on the producer fixes all three consumers. The bench does not run scripts, so it cannot show you this failure; your own project can, which is why the build-along makes you see it once on purpose.

Part 3 · covers cache keys, runner-side storage, hit and miss, and when a cache hurts

Cache is a hope, not a promise

5 min live

The caching page opens with the sentence this whole Part is built on: "Caching is an optimization, but it isn't guaranteed to always work." A cache is for "dependencies, like packages you download from the internet"; artifacts "pass intermediate build results between stages". A cache is stored where the runner is, and uploaded to object storage when a distributed cache is configured; by default it is not shared between protected and unprotected branches. Penwood's test jobs each run pip install -r requirements.txt. A cache keyed on that file means a run with the same requirements may find the packages already there. The word is "may".

Live When a cache helps and when it hurts 3 min▶

A cache helps when the content is reproducible from scratch, large to fetch, and the same across many runs. Python packages fit: the job can always pip install them, the download is slow, and requirements.txt changes rarely. A cache hurts in two cases. First, when the job depends on the cached content being present, because the caching page has already told you it may not be, and now a miss is a failure that nobody can reproduce by re-running. Second, when the key is too loose: the default key is default, one cache for the whole project, so a job that caches .cache/pip under the default key shares it with every other job and every branch that uses the default, and stale or mismatched packages creep in. Keying on requirements.txt ties the cache's identity to the file that defines its content: change the file, get a new key, start clean. On Free, every download a miss causes is paid in the 400 compute minutes a month (as of 2026-10-29), which is why a hit matters and why a miss must still pass.

Self-study Keys, four caches, and the protected-branch wall 2 min▶

A job can declare up to four caches, each with its own key and paths; Penwood needs one. The key can be a string (the default is default) or derived from files, and cache:key:files is the keyword the YAML reference lists for keying on a file's contents. The source map behind this page records only the default key, so read the reference entry once before you rely on the exact spelling; the mechanism, one key per distinct file contents, is what matters. By default the cache is not shared between protected and unprotected branches: a merge request pipeline from feature/orders-dedupe and a push to main fill two separate caches, so the first run on main after a requirements change is a miss even though the feature branch just warmed its own. The separation exists so an unprotected branch cannot poison what a protected one restores. Live with the extra miss; it costs minutes, not correctness.

Real world

The caching page documents the behaviour, and Penwood, constructed, meets it on day two: unit-tests ran green on the feature branch with a warm cache, the merge request merged, and the pipeline on main downloaded every package again. Nobody broke anything. Caches are not shared between protected and unprotected branches by default, and main is protected. The analyst who wrote unit-tests so that it only skipped a download on a hit, and never assumed one, watched the job take longer and pass. The analyst who had written "if the cache is there, skip install" would have watched it fail on main and pass on the branch, which is the worst kind of bug to be handed at 17:55.

Check yourself

Three questions

Clear all three and Builder session 4 gets stamped in your passport.

1 · PYTHON_VERSION is '3.12' in the YAML's default variables block and '3.11' in the project's CI/CD settings. The job defines nothing. Which value does the job see, and why?

The variables page lists project settings above every YAML variable, including the default block. A job walks the list from the top and takes the first definition it meets. Nothing in the repository shows the 3.11, which is why settings variables should never share a name with YAML ones.

2 · compile-models writes build/ in the build stage. unit-tests in the test stage lists it in needs. What is the smallest change that makes build/ appear in unit-tests?

The producer declares the artifact; later stages download it by default, and a needs entry downloads it too because artifacts: true is the default. A cache is not guaranteed to be present and is stored where the runner is, so B turns a build step into a hope. Jobs in one stage run in parallel in separate environments, so D shares nothing.

3 · A merge request pipeline on feature/orders-dedupe warmed the pip cache. The branch merges and the pipeline on main downloads every package again and passes. What happened?

The caching page documents the separation, and the default branch is protected by default. The key here is derived from requirements.txt, not the SHA. Packages were never an artifact. And a job written so a miss costs only minutes passes, which is exactly what it did.
