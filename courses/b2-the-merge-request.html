The merge request

Session 1 ended with a Developer refused on main and told to open a branch instead. Tonight that branch becomes Penwood's first merge request. A merge request is the same idea as a pull request: a proposed change, a diff, a conversation, a pipeline result and a merge button on one page. Two mechanisms underneath are GitLab's own and shape every later session: approvals that exist on Free but do not block the merge, and a pipeline that belongs to the merge request itself, runs on the source branch and never sees CI_COMMIT_BRANCH. Penwood, a constructed five-person logistics-analytics team, opens the request from feature/orders-dedupe and reads what its pipeline tab will show against the bench's r3 job table.

Part 1 · covers what the merge request page gathers in one place

Same idea, different name

5 min live

What a repository, an issue and a pull request are belongs to the GitHub course's branches and PRs session; this page takes only GitLab's side of the seam, the deltas. The merge requests page calls the merge request "a central location for your team to review code, have discussions, and track code changes", and that is the whole of the rename: a proposed change from a source branch into a target branch, with the description, the comment threads, the commits, the pipelines and the diff on one page, and a merge button at the bottom that the branch rule decides who may press.

Live Where a thread lives and when it closes 3 min▶

A comment made on a line in Changes and a comment made at the bottom of Overview are the same kind of thing: a thread on the merge request. Changes shows it beside the line it was about; Overview shows every thread in time order with the line of code quoted. The habit that matters for Penwood is to leave review on the line, because the next push moves the conversation forward with the code and the reviewer can see whether the line changed. Resolving a thread is a click by whoever is satisfied, usually the reviewer. Whether an unresolved thread may block the merge is a project setting; the settings page for it was not read at source on 2026-10-29, so open your project's merge request settings and read the option's own wording before you make it a team rule.

Self-study Draft, squash and the merge method: settings exist, read them yourself 2 min▶

Three things a team coming from a pull request habit will look for: marking a request as a draft so it cannot be merged yet, squashing the source branch's commits into one when merging, and the merge method itself (a merge commit or a linear history). All three exist in GitLab as options on the merge request or in the project's merge request settings. None of their documentation pages were read at source on 2026-10-29, so no sentence about their exact behaviour is printed here. The honest instruction is: open the project's merge request settings, read the three options' own descriptions, and decide Penwood's rule in session 3 after you have seen the first real merge. Learning to say "the docs page says" instead of "I think it does" is half of being the person a team trusts with its settings.

Real world

Constructed: Raj, Maintainer in data, opens Changes on Penwood's !1 and leaves a thread on the line that dedupes by order id alone, asking about late-arriving corrections. Mei pushes a second commit keyed on order id and version. The Commits tab shows two, the Changes tab shows the new line, Raj's thread still sits beside the old one with a note that the line changed, and the Overview shows the whole exchange. Nobody copied anything between tabs. That is the mechanism the merge requests page is describing when it says "a central location": one branch, one record, several views.

Part 2 · covers who can approve on Free and what the approval does

Approvals on Free are optional

6 min live

The approvals page is precise. On Free, users with at least the Developer role can approve a merge request, and "These approvals are optional and don't prevent merging without approval". Required approval rules, the kind that grey out the merge button until two people from a named group have approved, are Premium and Ultimate, as is approval by Code Owners. So on Free an approval is a signal, not a lock, and the lock Penwood actually has is the branch rule: only Maintainers merge into main.

Live Who approves, who merges, at Penwood 3 min▶

Because the approval does not lock anything on Free, Penwood writes down what it means instead. Constructed convention: one approval from someone who did not write the change, left after reading Changes, before a Maintainer merges. The permissions page gives the roles that make this work: Developer can "Push code to non-protected branches, create merge requests, and run CI/CD pipelines"; Maintainer can "Manage branches, merge requests, CI/CD settings, and project members". So Mei and the analyst, both Developers, open and approve; Raj, Maintainer in data, and the data lead, Owner, merge. The finance partner, Reporter, can read the diff and comment but cannot approve, which is the right shape for a partner who should be asked but not made responsible.

Self-study When the signal is not enough 2 min▶

A convention holds while the team is five people who sit together. The moment it has to hold against someone in a hurry, or against an auditor's question "show me that nobody merged without review", the Free approval has nothing to show. That is the honest shape of the Premium decision: required approval rules and Code Owner approval are Premium and Ultimate, at $29 per user per month billed annually as of 2026-10-29; re-verify the tier page before relying on it. Leader session 5 weighs that against the Free substitutes. On the Builder track the substitute you can build is session 6's blocking manual deploy: a merge may slip through early, but production does not move until a named person clicks.

Real world

Constructed: the analyst approves !1 after a quick read, and Mei, who wrote it, sees the green approval and reaches for Merge. The button is not there for her: she is a Developer, and the branch rule hands the merge of main to Maintainers. Raj gets a ping, reads Changes, and asks for the version-keyed fix from Part 1 before merging. The approval said "one person looked"; the branch rule said "a Maintainer decides"; both did exactly what the docs say they do, and neither pretended to be the other.

Part 3 · covers merge_request_event, the source branch and the unset variable

The merge request pipeline

6 min live

A pipeline can be started by a push to a branch or by a merge request event, and GitLab treats them as different kinds of pipeline. The merge request pipelines page says the configuration "must include job rules or workflow rules that match" $CI_PIPELINE_SOURCE == "merge_request_event", that these pipelines "Run on the contents of the source branch only", and that they "Display a merge request label in pipeline lists". The predefined variables reference adds the consequence that catches everyone once: CI_COMMIT_BRANCH is "Available in branch pipelines, including pipelines for the default branch" and is not set in merge request pipelines. Any rule that compares it never matches there.

Live What the unset variable does to Penwood's jobs 3 min▶

Six of Penwood's fourteen jobs carry a rule that compares CI_COMMIT_BRANCH with CI_DEFAULT_BRANCH: publish-image, publish-docs, deploy-staging and deploy-production, plus docs-build on a changes rule and nightly-backfill on the schedule source. In a merge request pipeline the branch variable is unset, so those four comparisons can never be true, and the job rules page says what follows: "If no rules match, the job is not added to the pipeline". Not failed, not skipped with a grey icon, simply absent. That is the design, not an accident: a merge request should prove the change, and publishing and deploying belong to main. The bench's r3 rung measures exactly this: 8 jobs run, 6 never added, 19:17 on the wall clock, 41.17 compute minutes. Session 5 writes the rules; tonight you only need to recognise the shape when you see a merge request pipeline with fewer jobs than main has.

Self-study The variables a merge request pipeline does have 2 min▶

The predefined variables reference lists what replaces the missing branch name: CI_MERGE_REQUEST_IID, the request's number in the project, and CI_MERGE_REQUEST_TARGET_BRANCH_NAME, which for Penwood's !1 is main. CI_COMMIT_REF_NAME, "The branch or tag name for which project is built", is set in every pipeline. So a job that needs to know "am I in a merge request, and into what" has its answers; a job that asks "which branch am I on" using CI_COMMIT_BRANCH is asking the branch pipeline's question in the wrong room. The rules:changes keyword, used by docs-build and data-quality-tests, also behaves differently here: in a merge request pipeline it compares against the target branch, in a branch pipeline against the previous commit. Merged results pipelines and merge trains exist on top of all this and are deliberately outside these eight sessions.

Real world

Documented, not constructed: the job rules page describes the duplicate-pipeline trap. If a job's rules end in a bare rule with no if, a push to a branch that has an open merge request starts two pipelines, a branch pipeline and a merge request pipeline, both running the same jobs and both charging compute minutes. The fix the page gives is workflow:rules at the top of the file, and Penwood's second workflow rule is that fix: when a branch has an open merge request, when: never for the branch event. The bench prices the silenced pipeline at 0 compute minutes, which on a 400-minute Free quota as of 2026-10-29 is not a small thing.

Check yourself

Three questions

Clear all three and Builder session 2 gets stamped in your passport.

1 · Penwood is on GitLab.com Free. The analyst, a Developer, approves !1. What has that approval changed about whether the request can be merged?

The approvals page says Free approvals are optional and do not prevent merging. The lock on main is the protected branch rule, which hands push and merge to Maintainers by default. Required approval rules that grey out the button are Premium and Ultimate.

2 · A job's only rule is if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH. What happens to it in Penwood's merge request pipeline for !1?

The predefined variables reference makes CI_COMMIT_BRANCH available in branch pipelines and not in merge request pipelines. The job rules page: "If no rules match, the job is not added to the pipeline". That is why r3 never adds publish-image, publish-docs, deploy-staging and deploy-production.

3 · Mei pushes to feature/orders-dedupe while !1 is open. Penwood's workflow rules are the four in the build-along. How many pipelines start, and why?

Rules are evaluated in order until the first match, once per event. The merge request event stops at rule 1 and a pipeline is created on the source branch. The branch event fails rule 1, matches rule 2 and is excluded. Without rule 2 both would run: the documented duplicate-pipeline trap that workflow:rules exists to prevent.
