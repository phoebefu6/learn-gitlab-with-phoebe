Learn GitLab · Builder session 5 of 8

Rules, needs and the DAG

Session 3 gave Penwood a pipeline that goes green in 30:08 because every stage waits for the slowest job of the stage before it. Tonight two keywords change that. needs tells a job which jobs it actually depends on, so it starts the moment they finish and the stage boundary stops mattering. rules tells GitLab whether a job belongs in this pipeline at all, read top to bottom, stopping at the first match. Penwood, a constructed five-person logistics-analytics team on GitLab.com Free, takes its 14 jobs from 30:08 with stages only, to 26:22 with needs, to 19:17 and eight jobs when rules meet a merge request. Every one of those numbers comes from the bench in session 8, which parses the real YAML and runs nothing on GitLab; the durations are a constructed run log.

Part 1 · covers rules, if, changes, when: never and the duplicate-pipeline trap

First match wins

6 min live

The job rules page says it in two sentences worth memorising: "Rules are evaluated in order until the first match" and "If no rules match, the job is not added to the pipeline". A rule is a condition, usually if: on a predefined variable or changes: on a file path, and an optional when. The first rule whose condition is true decides the job's fate and the rest are never read. A matching rule with when: never removes the job; a matching rule with no when keeps the job's own when, which defaults to on_success. If you know the if: of a workflow file from the Actions session in GitHub for builders, leave it there; only GitLab's rules are taught here, because the stop-at-first-match reading is the part that bites.

Live if, changes, and the order you write them in 3 min▶

Penwood's unit-tests job carries two rules: run in a merge request pipeline, and run on the default branch. Written in that order they read naturally, and because neither has a when, a match keeps the job's default on_success. The order only matters once a rule carries when: never or when: manual: put the exclusion first and it wins before anything below gets a chance; put it last and it only catches what nothing above caught. rules:changes is the other condition worth knowing well. The job rules page says it compares against the merge request's target branch in a merge request pipeline and against the previous commit in a branch pipeline, and that it is always true on a new branch or when there is no push event. So docs-build with changes: docs/**/* stays out of a merge request that touched only pipelines/, and comes in the moment a runbook changes. rules:exists is outside tonight's subset.

Self-study when: the six values, and which two belong to rules only 2 min▶

The YAML reference lists on_success (the default), on_failure, always, never, manual and delayed with a start_in of one second to one week. never is only meaningful inside rules or workflow:rules, since a job that is always never is a job you should delete. manual behaves differently depending on where it sits, and that difference is session 6's whole third Part: outside rules, a manual job has allow_failure: true by default and the pipeline can finish green around it; inside rules, allow_failure defaults to false and the docs say "The pipeline stops at the stage where the job is defined", status blocked. Penwood's deploy-production puts when: manual inside its rule on purpose, so a production deploy blocks rather than being quietly optional.

Real world

The job rules page documents the trap directly: a rules list that ends in a bare - when: always (or any rule that matches both) can start a branch pipeline and a merge request pipeline on the same push, two pipelines, double the compute minutes, two results for one commit. The documented fix is workflow:rules at the top of the file, which decides whether a pipeline runs at all; "When no rules evaluate to true, the pipeline does not run". Penwood's second workflow rule is if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS with when: never: a push to a feature branch that already has an open merge request creates no branch pipeline. On the bench that context prints "No pipeline" and zero compute minutes. The merge request pipeline still runs, which is the one you wanted.

Part 2 · covers needs, needs: [], the critical path, and why stages alone are slow

Needs skip the queue

6 min live

Stages are a queue. The YAML reference: "Jobs in the same stage run in parallel", and the next stage starts only after the previous stage's jobs succeed. That is simple to read and, as the pipeline architectures page admits of basic pipelines, "not the most efficient". needs replaces the stage boundary with an edge: name the jobs this job depends on and it may start the moment they finish, "even starting earlier than other jobs in the same stage". The pipeline becomes a directed acyclic graph, a DAG, and the wall clock becomes the longest path through it, the critical path. On Penwood's constructed pipeline the bench measures that as 30:08 with stages only and 26:22 with needs, for the same 13 jobs and the same 66.30 compute minutes.

Live Write needs as the truth about inputs, not as a speed trick 3 min▶

The needs page: "An array of jobs (maximum of 50 jobs)". You may name jobs in the same stage, and needs: [] means the job starts "as soon as the pipeline is created". Artifacts of needed jobs are downloaded by default, artifacts: true, which is why the compile-models output from session 4 keeps reaching the tests. The discipline is to write what is true: integration-tests needs build-image and compile-models because it runs the image against the compiled models; unit-tests needs only compile-models; scan-dependencies and nightly-backfill need nothing, so needs: []. Get that right and the speed follows: the bench's r2 critical path is lint-yaml, build-image, integration-tests, publish-image, deploy-staging, and compile-models starts at 1:47 the instant lint-sql finishes rather than after the whole lint stage. Which tests Penwood should run is a different question, answered in DataOps: data testing and contracts; this page only decides where in the graph a test job sits.

Self-study Two conventions that belong to the bench, not to GitLab 2 min▶

Two behaviours the bench shows are its own, and are labelled as such on the widget. First: a needs reference to a job in a later stage is reported as an error. The needs reference read on 2026-10-29 says same-stage references are allowed and does not state the later-stage case, so the bench's convention is the strict reading, not GitLab's documented behaviour. Second: a manual job is never scheduled by the bench; it "waits for a click", and any job downstream of it is reported as waiting, because the reference does not fix a duration for a manual gate. A third assumption sits beside them: under a runner cap the bench starts ready jobs longest-remaining-path first, ties by stage then definition order. GitLab does not document a queue order for a runner fleet. When you read a number off the bench, know which of the three it leans on; the r1, r2 and r3 wall clocks here lean on none of them, since the runners are unlimited and deploy-production is simply listed as manual.

Real world

Constructed: Raj, Penwood's Maintainer, adds needs to every job expecting the compute-minutes line on the usage page to drop. It does not. The bench's r1 and r2 both print 66.30 compute minutes, because compute minutes are serial seconds over sixty at cost factor 1, and the same thirteen jobs ran for the same constructed durations. What moved was the wall clock, from 30:08 to 26:22, which is what the team feels waiting for a merge. The quota line is Part 3's job, where rules decide a job does not run at all. Against the Free tier's 400 compute minutes a month as of 2026-10-29, that is the only lever that matters; re-verify the tier page before relying on it.

Part 3 · covers the missing-needs error, optional: true, and the six jobs r3 never added

The job that is not there

5 min live

Put the two keywords together and a new failure appears. Rules can remove a job from a pipeline; needs can name that job. The needs page gives the result verbatim: pipeline creation fails with "'unit_tests' job needs 'compile' job, but 'compile' does not exist in the pipeline". The escape hatch is optional: true on the needs entry, which lets the needed job be absent. And the quieter consequence is the one to carry home: when rules leave a job out, it is not skipped, not failed, not grey; it is simply not in the pipeline. The bench's r3, a merge request with pipelines/ changed, runs 8 of Penwood's 14 jobs, never adds 6, and passes.

Live Why r3 drops six jobs, and why four of them are the same reason 3 min▶

The bench's r3 context is a merge request from feature/orders-dedupe with pipelines/orders/dedupe.py and a unit test changed. docs-build leaves because docs/ did not change. nightly-backfill leaves because its only rule is CI_PIPELINE_SOURCE == "schedule". The other four, publish-image, publish-docs, deploy-staging and deploy-production, all carry the rule CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH, and the predefined variables page says CI_COMMIT_BRANCH is available in branch pipelines and not set in merge request pipelines. Unset compared with main is false; no rule matches; four jobs are never added. That is the behaviour you want for a merge request, nothing gets published or deployed from an unmerged branch, and it is also why a merge request pipeline is shorter and cheaper: 8 jobs, 19:17, 41.17 compute minutes against the push to main's 49.25.

Self-study Reading a never-added job on the real pipeline page 2 min▶

GitLab's pipeline page shows the jobs that exist. A job the rules left out is not drawn as skipped or greyed; it is absent, and the pipeline's job count is smaller. So the honest reading habit is to know how many jobs a pipeline of this type should have and to count. For Penwood the expected counts come off the bench: 8 in a merge request with pipelines/ changed, 11 on a push to main, 11 on a schedule. The bench's break button makes the point unmissable: one character wrong in a rule, merge_request for merge_request_event, and unit-tests is never added, 7 jobs run instead of 8, wall clock unchanged at 19:17, pipeline passed. Nothing is red because, once more, a job that was never added cannot fail. Leader session 4 teaches the same habit from the manager's side.

Real world

Constructed: Mei gives compile-models a rule so it runs only when models/ changes, to save minutes. The next merge request touches only pipelines/. Pipeline creation fails on the spot: unit-tests, data-quality-tests and integration-tests all need compile-models, and the error names a needing job and the job it cannot find. Nothing ran, so it cost zero minutes and a red banner. The repair is a decision, not a keyword: either compile-models runs in every pipeline that tests, or the three tests get optional: true and you accept that they may run without fresh models. Penwood picks the first; the models are what the tests test. The bench's planted-fault file reproduces the error with two toy jobs so you can read the exact text.

Check yourself

Three questions

Clear all three and Builder session 5 gets stamped in your passport.

1 · A job has two rules in this order: if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH with when: never, then if: $CI_COMMIT_BRANCH. A push lands on main. What happens to the job?

"Rules are evaluated in order until the first match." The first rule matches on main and carries when: never, so the job is excluded and the second rule is never read. Swap the two lines and the job runs on every branch including main.

2 · Penwood adds needs to all fourteen jobs and pushes to main. On the bench the wall clock goes from 30:08 to 26:22. What happens to the compute minutes?

Compute minutes are serial seconds over sixty at cost factor 1. Needs change when jobs start, not how long they run or how many run. Only rules, which leave jobs out, change the bill: r3's 41.17 is a merge request pipeline with six jobs never added.

3 · unit_tests has needs: [compile]. A rule leaves compile out of this pipeline. What does GitLab do, and what is the keyword that changes it?

The needs page gives the error text verbatim, and the pipeline is not created at all. optional: true on the needs entry lets the needed job be missing; whether the dependent job should then run without it is a decision about the job, not about GitLab.
